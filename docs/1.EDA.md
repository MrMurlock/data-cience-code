# EDA — Reporte y presentación

Esta fase corresponde al análisis exploratorio de datos (EDA) del dataset documentado en `DATASET.md`.

El objetivo es caracterizar el dataset, evaluar su calidad, estudiar las distribuciones de sus variables y analizar relaciones relevantes entre ellas. Los resultados deben servir para fundamentar las transformaciones de datos realizadas y las decisiones posteriores de análisis.

El EDA debe producir tres resultados relacionados:

1. Un conjunto de datos procesado para el análisis.
2. Artefactos de análisis, principalmente tablas y gráficos.
3. Un reporte Markdown y una presentación Marp que utilicen dichos artefactos.

Python debe encargarse del procesamiento, cálculos estadísticos y generación de tablas y gráficos. El contenido narrativo del reporte y de la presentación debe escribirse en Markdown a partir de los resultados obtenidos por el pipeline; Python no debe generar automáticamente el texto narrativo.

`DATASET.md` es la fuente de referencia para comprender el origen, significado y estructura de los datos.

## Flujo general

```text
dataset/raw
    │
    ▼
preprocessing inicial
    │
    ▼
dataset preparado
    │
    ▼
EDA
    ├── calidad de datos
    ├── análisis univariado
    └── análisis bivariado
    │
    ├───────────────┐
    ▼               ▼
tables             plots
    │               │
    └───────┬───────┘
            ▼
      Reporte Markdown
            │
            ▼
       Presentación Marp
```

El análisis puede revelar problemas o transformaciones adicionales que no hayan sido identificados durante el preprocessing inicial. Estas decisiones deben quedar documentadas y, cuando correspondan a transformaciones reproducibles del dataset, incorporarse al pipeline de preprocessing.

## 1. Preparación inicial

El pipeline debe cargar el dataset original y aplicar las transformaciones de preprocessing necesarias antes del análisis.

Las transformaciones iniciales conocidas incluyen:

* Separar `Blood Pressure` en `bp_systolic` y `bp_diastolic`.
* Completar valores faltantes de `Sleep Disorder` con la categoría correspondiente a ausencia de trastorno.
* Estandarizar `BMI Category`, incluyendo la unificación de `Normal Weight` y `Normal`.
* Eliminar `Person ID` por no aportar información analítica.
* Mantener las variables derivadas de presión arterial para su análisis.

Una vez creadas `bp_systolic` y `bp_diastolic`, `Blood Pressure` no debe utilizarse como variable numérica en los análisis de correlación, ya que es una representación textual de las dos variables derivadas.

El pipeline debe conservar una separación clara entre:

* transformaciones de limpieza/preparación;
* análisis exploratorio;
* decisiones derivadas de los hallazgos del EDA.

Las variables derivadas como `age_group` o `quality_group`, si se utilizan, deben considerarse feature engineering y no deben incorporarse automáticamente al preprocessing sin justificar su utilidad para el análisis.

## 2. Calidad de los datos

El análisis debe evaluar al menos:

* dimensiones del dataset;
* tipos de datos;
* valores faltantes;
* registros duplicados;
* valores únicos y categorías;
* valores fuera de rangos plausibles;
* inconsistencias entre categorías;
* valores extremos y posibles outliers.

Los resultados deben producir tablas o métricas que permitan respaldar las conclusiones del reporte.

Los outliers no deben eliminarse automáticamente. Primero deben identificarse y analizarse para determinar si representan errores, valores plausibles o casos que requieren consideración especial.

## 3. Análisis univariado

El análisis univariado debe estudiar cada variable individualmente.

### 3.1 Variables numéricas

Para las variables numéricas se deben considerar:

* medidas de tendencia central;
* dispersión;
* mínimo y máximo;
* cuartiles;
* distribución;
* asimetría;
* curtosis;
* posibles outliers.

Se deben generar gráficos apropiados, principalmente histogramas y boxplots cuando aporten información relevante.

El análisis debe identificar distribuciones particulares. Por ejemplo, una variable con alta asimetría o presencia de valores extremos debe ser destacada en el reporte.

### 3.2 Variables categóricas

Para las variables categóricas se deben analizar:

* cantidad de categorías;
* frecuencia absoluta;
* frecuencia relativa;
* categorías dominantes;
* categorías poco representadas;
* posibles desbalances.

Se deben utilizar gráficos de frecuencia cuando faciliten la interpretación.

No se deben interpretar categorías codificadas numéricamente como variables continuas.

## 4. Análisis bivariado

El análisis bivariado debe seleccionar el método de análisis según el tipo de las dos variables involucradas.

El objetivo no es aplicar todos los métodos a todas las combinaciones posibles, sino identificar relaciones relevantes mediante exploración visual y posteriormente cuantificarlas mediante métodos estadísticos apropiados.

### 4.1 Numérica × numérica

Para relaciones entre variables numéricas se deben utilizar:

* scatter plots;
* correlación de Pearson para relaciones lineales;
* correlación de Spearman cuando sea relevante evaluar relaciones monotónicas;
* análisis visual de outliers y dispersión.

Las relaciones particularmente relevantes deben cuantificarse y comentarse en el reporte.

Entre las relaciones de interés para este dataset se encuentran:

* `Sleep Duration` × `Quality of Sleep`;
* `Sleep Duration` × `Physical Activity Level`;
* `Sleep Duration` × `Stress Level`;
* `Sleep Duration` × `Heart Rate`;
* `bp_systolic` × `bp_diastolic`.

La correlación no debe interpretarse como causalidad.

### 4.2 Categórica × numérica

Cuando una variable categórica divide las observaciones en grupos y la otra es numérica, se deben utilizar representaciones como boxplots o violin plots.

La comparación estadística debe depender de la cantidad de grupos y de las características de los datos:

* dos grupos: t-test o Mann-Whitney según corresponda;
* más de dos grupos: ANOVA o Kruskal-Wallis según corresponda.

Cuando se utilicen pruebas estadísticas, deben considerarse sus supuestos y reportarse, cuando corresponda, medidas de tamaño de efecto.

Ejemplos de relaciones relevantes:

* `Sleep Disorder` × `Sleep Duration`;
* `Sleep Disorder` × `Quality of Sleep`;
* `Sleep Disorder` × `Stress Level`;
* `Sleep Disorder` × `Heart Rate`;
* `Occupation` × variables relacionadas con sueño;
* `BMI Category` × variables relacionadas con sueño.

Un resultado estadísticamente significativo no debe interpretarse automáticamente como una relación fuerte ni como causalidad.

### 4.3 Categórica × categórica

Para relaciones entre variables categóricas se deben utilizar:

* tablas de contingencia;
* proporciones por categoría;
* chi-cuadrado de independencia;
* Cramér's V cuando corresponda para evaluar el tamaño de la asociación.

Entre las relaciones potencialmente relevantes se encuentran:

* `Occupation` × `Sleep Disorder`;
* `BMI Category` × `Sleep Disorder`;
* `Gender` × `Sleep Disorder`.

La prueba de chi-cuadrado debe interpretarse considerando sus supuestos, especialmente los conteos esperados de las categorías.

## 5. Selección de relaciones

El pipeline no debe generar indiscriminadamente todas las combinaciones posibles de variables y pruebas estadísticas.

El análisis debe seguir preferentemente este flujo:

```text
Exploración visual
        │
        ▼
Identificación de relación potencialmente relevante
        │
        ▼
Selección del método estadístico apropiado
        │
        ▼
Cuantificación
        │
        ▼
Revisión de outliers y distribución
        │
        ▼
Interpretación
```

La selección debe priorizar:

* relaciones sugeridas por los gráficos;
* variables relevantes para el dominio;
* relaciones fuertes o potencialmente interesantes;
* relaciones necesarias para explicar los principales hallazgos del dataset.

No deben presentarse cientos de pruebas estadísticas sin interpretación.

## 6. Artefactos generados

El pipeline debe producir artefactos reutilizables por el reporte y la presentación.

Estos deben incluir, según corresponda:

* tablas en CSV;
* gráficos en un formato apropiado para Markdown/Marp;
* métricas estadísticas;
* resultados de pruebas estadísticas;
* dataset procesado.

Los artefactos deben tener nombres descriptivos y una organización predecible.

El pipeline no debe generar automáticamente el texto narrativo del reporte ni de la presentación.

El Markdown debe poder referenciar los artefactos generados para evitar duplicar cálculos o resultados.

## 7. Reporte EDA

El reporte debe tener una estructura analítica y utilizar los artefactos generados por el pipeline como evidencia.

### Estructura

```text
EDA — Sleep Health and Lifestyle Dataset

1. Introducción
   1.1 Objetivo
   1.2 Descripción del dataset

2. Preparación inicial
   2.1 Carga y tipos de datos
   2.2 Transformaciones iniciales
   2.3 Tratamiento de valores faltantes

3. Calidad de los datos
   3.1 Valores faltantes
   3.2 Duplicados
   3.3 Valores inválidos
   3.4 Valores extremos

4. Análisis univariado
   4.1 Variables numéricas
   4.2 Variables categóricas

5. Análisis bivariado
   5.1 Numérica–numérica
   5.2 Categórica–numérica
   5.3 Categórica–categórica

6. Principales hallazgos
   6.1 Relaciones relevantes
   6.2 Distribuciones relevantes
   6.3 Outliers
   6.4 Desbalance de categorías
   6.5 Variables potencialmente redundantes

7. Decisiones de procesamiento
   7.1 Transformaciones realizadas
   7.2 Variables eliminadas
   7.3 Consideraciones para análisis posteriores

8. Conclusiones
```

El reporte debe priorizar interpretación sobre cantidad de gráficos. Cada gráfico o tabla incluido debe aportar evidencia para una observación o conclusión.

Las conclusiones deben distinguir claramente entre:

* observaciones descriptivas;
* asociaciones estadísticas;
* posibles interpretaciones;
* decisiones de procesamiento.

No deben realizarse afirmaciones causales a partir de análisis observacional.

## 8. Presentación

La presentación debe comunicar los resultados principales del EDA de manera más sintética que el reporte.

Debe utilizar Marp y priorizar:

* visualizaciones;
* resultados estadísticos relevantes;
* hallazgos principales;
* conclusiones;
* decisiones importantes de preprocessing.

La presentación debe contener menos texto que el reporte. No debe reproducir todas las tablas, pruebas o explicaciones metodológicas del informe.

Una estructura sugerida es:

```text
1. Contexto y objetivo
2. Dataset
3. Preparación y calidad de datos
4. Principales características univariadas
5. Relaciones numéricas relevantes
6. Relaciones categóricas relevantes
7. Principales hallazgos
8. Decisiones de procesamiento
9. Conclusiones
```

Cada diapositiva debe comunicar una idea principal. Los gráficos deben utilizarse cuando permitan explicar esa idea mejor que el texto.

## 9. Principales hallazgos esperados

El análisis inicial del dataset ya permite identificar algunas relaciones que deben ser verificadas y cuantificadas durante la implementación:

* `bp_systolic` y `bp_diastolic` presentan una relación lineal fuerte, esperable por representar componentes de una misma medición.
* `Sleep Duration` presenta una relación positiva con `Quality of Sleep`.
* `Sleep Duration` presenta una relación positiva con `Physical Activity Level`.
* `Sleep Duration` presenta una relación negativa con `Stress Level`.
* `Sleep Duration` presenta una relación negativa con `Heart Rate`, con presencia de algunos valores atípicos.
* `Heart Rate` presenta una distribución con asimetría positiva y posibles valores extremos.
* Las variables categóricas presentan distintos niveles de desbalance; `Gender` es aproximadamente equilibrada, mientras que `Occupation` y `Sleep Disorder` presentan distribuciones más concentradas.

Estos puntos son hipótesis exploratorias iniciales y deben ser respaldados por los resultados del pipeline. El agente no debe asumir que una relación es estadísticamente significativa solamente porque se observa visualmente.

## 10. Criterios de implementación

La implementación debe priorizar código simple, modular y reproducible.

El pipeline debe separar las responsabilidades de:

* carga de datos;
* preprocessing;
* análisis estadístico;
* generación de tablas;
* generación de gráficos;
* preparación de artefactos para documentación.

Las funciones deben tener responsabilidades específicas y evitar concentrar todo el análisis en `pipeline.py`.

`pipeline.py` debe actuar principalmente como punto de composición y ejecución del pipeline.

El reporte y la presentación deben consumir los resultados generados por el pipeline en lugar de recalcularlos manualmente.

El texto narrativo debe permanecer fuera del código Python. El código debe producir datos y artefactos que permitan al agente redactar el contenido del reporte y la presentación con evidencia reproducible.

La función `render` forma parte del pipeline EDA como una etapa separada, y permite regenerar los documentos sin recalcular el análisis. La implementación debe mantener las decisiones concretas (nombres de módulos, flags del CLI) sin sobre-especificar la estructura interna.

## 11. Generación y renderizado del reporte

El pipeline EDA debe separar la generación de resultados del renderizado de los documentos.

El análisis debe generar artifacts reutilizables que posteriormente puedan ser consumidos por documentos Markdown. El pipeline debe exponer una función de renderizado independiente que permita regenerar el reporte a partir de los artifacts existentes, sin necesidad de volver a ejecutar el análisis completo.

El flujo esperado es:

```text
dataset
    │
    ▼
EDA pipeline
    │
    ├── preprocessing
    ├── análisis
    └── generación de artifacts
            │
            ├── tables
            ├── metrics
            └── images
            │
            ▼
       report template
            │
            ▼
         render()
            │
            ▼
       report final
```

### 11.1 Artifacts

Los resultados calculados por el pipeline deben almacenarse como artifacts identificables mediante nombres lógicos.

La implementación inicial debe soportar tres tipos:

* `table`: resultados tabulares, inicialmente almacenados como CSV.
* `metric`: valores escalares o métricas calculadas.
* `image`: gráficos o imágenes generados por el análisis.

Ejemplos de nombres lógicos:

```text
numeric_summary
missing_values
sleep_quality_pearson
sleep_duration_quality
heart_rate_distribution
```

Los documentos no deben depender directamente de las rutas físicas de estos archivos. El renderer debe resolver el nombre lógico del artifact a su ubicación correspondiente.

La organización física de los artifacts puede ser definida por la implementación, pero debe mantener una separación clara entre tablas, métricas e imágenes.

### 11.2 Templates Markdown

El reporte debe escribirse como un documento Markdown editable por un usuario o agente.

El Markdown incluye referencias dinámicas a artifacts mediante un mecanismo propio de renderer ligero (`utils/render.py`), que resuelve las directivas del documento:

```markdown
# Análisis univariado

## Variables numéricas

La siguiente tabla resume las principales estadísticas descriptivas:

{{ table("numeric_summary") }}

La correlación entre duración y calidad del sueño es
{{ metric("sleep_duration_quality_pearson") }}.

{{ image("sleep_duration_quality") }}
```

Directivas soportadas:

* `{{ table("name") }}`: convierte el artifact tabular a una tabla Markdown.
* `{{ table("name", offset, limit) }}`: variante para presentaciones Marp, que permite dividir una tabla larga en varias láminas.
* `{{ metric("name") }}`: inserta el valor de la métrica renderizado como texto.
* `{{ image("name") }}`: genera la referencia Markdown de la imagen con la ruta relativa al documento de salida.
* `{{ image("name", width) }}`: variante que fija el ancho de la imagen en píxeles (genera `alt="w:N"`, sintaxis de Marp), útil para dimensionar gráficos en láminas.

Los nombres utilizados en el template deben ser nombres lógicos y no nombres de archivos. El renderer registra los artifacts no resueltos y los reporta al final del render para que el agente pueda detectar referencias rotas.

### 11.3 Renderizado

El pipeline dispone del render como etapa independiente, implementado en `render_eda.py` del pipeline EDA:

```python
render_reports()   # template + artifacts → documento final
```

Esta función debe:

1. cargar el template Markdown;
2. resolver las referencias a artifacts;
3. generar el Markdown final;
4. guardar el resultado como output.

El renderizado no debe ejecutar nuevamente el análisis estadístico ni regenerar los artifacts.

Esto debe permitir dos operaciones independientes:

```text
Ejecutar análisis:
    dataset → análisis → artifacts

Regenerar documento:
    artifacts + template → render() → report
```

De esta forma, modificar el contenido narrativo del reporte no requiere volver a ejecutar el análisis, mientras que actualizar los datos permite regenerar los artifacts y posteriormente volver a renderizar el mismo template.

El Markdown fuente debe considerarse el documento editable. El Markdown generado por `render()` debe considerarse un output y no debe editarse manualmente.

### 11.4 Separación de responsabilidades

La generación de artifacts y el renderizado deben mantener responsabilidades separadas.

El análisis EDA es responsable de:

* cargar y preparar los datos;
* realizar los análisis;
* calcular estadísticas;
* generar tablas;
* generar métricas;
* generar gráficos;
* guardar los artifacts.

El template Markdown es responsable de:

* definir la estructura del reporte;
* proporcionar la narrativa;
* interpretar los resultados;
* presentar conclusiones;
* seleccionar qué artifacts incluir.

El renderer es responsable de:

* cargar el template;
* resolver los nombres lógicos de los artifacts;
* convertir artifacts al formato requerido por Markdown;
* generar el documento final.

El renderer no debe realizar análisis estadístico ni generar interpretaciones.

### 11.5 Regeneración del reporte

La implementación debe permitir regenerar el reporte de manera determinista a partir de los artifacts y del template.

El flujo normal del pipeline puede ejecutar tanto el análisis como el renderizado (comando por defecto), con flags para separar las etapas:

```bash
uv run python -m data_cience_code.pipelines.eda                 # análise completo + render
uv run python -m data_cience_code.pipelines.eda --render-only   # solo render (artifacts existentes)
uv run python -m data_cience_code.pipelines.eda --no-render     # solo análise
```

Con `--render-only` los templates se regeneran de manera determinista a partir de los artifacts ya existentes.

Pero `render()` debe poder ejecutarse independientemente cuando los artifacts ya existen.

Esto permite modificar únicamente el contenido del reporte y regenerarlo sin repetir cálculos costosos o modificar los resultados almacenados.

### 11.6 Uso futuro

La infraestructura de artifacts y renderizado debe diseñarse como una utilidad reutilizable para futuros trabajos de ciencia de datos.

El sistema no debe asumir que los artifacts pertenecen exclusivamente al EDA. Otros pipelines podrán generar sus propias tablas, métricas e imágenes y utilizar el mismo mecanismo de renderizado.

El mismo mecanismo podrá utilizarse posteriormente para preparar documentos Markdown destinados a diferentes salidas, como reportes detallados o presentaciones Marp. El contenido y nivel de detalle de cada documento debe permanecer en su propio template, aunque ambos puedan consumir los mismos artifacts.

Para la presentación, la exportación a PPTX es opcional (`--pptx`) y se realiza con Marp CLI solo si está instalada; el pipeline produce siempre el Markdown final de Marp.
